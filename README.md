# LTAZ MCP Tools

A WordPress plugin that brings the Lee's Trees site's MCP tool surface to parity
with the PPS staging server.

Lee's Trees currently exposes **43** MCP tools — the stock AI Engine surface
(`mcp_ping`, `mwai_*`, `wp_*`). PPS staging exposes **106**. This plugin closes
the custom-code half of that gap by adding the **48 `pps_*` tools**; the
remaining 15 are an AI Engine setting, not code (see
[The other 15 tools](#the-other-15-tools)).

## Install

1. Copy the `ltaz-mcp-tools/` directory into `wp-content/plugins/` on the Lee's
   Trees site.
2. Activate **LTAZ MCP Tools** from Plugins.
3. Confirm AI Engine's MCP module is enabled — the plugin registers through
   AI Engine's `mwai_mcp_tools` / `mwai_mcp_callback` filters and does nothing
   without it.
4. Reconnect the MCP client so it re-reads the tool list.

Requires PHP 8.0+ and AI Engine (the site has 3.7.1).

## What you get

All 48 tools, with the same names and the same argument names as staging, so any
prompt or automation written against PPS works here unchanged.

| Group | Count | Tools |
|---|---|---|
| Navigation menus | 6 | `list_nav_menus`, `get_nav_menu`, `create_nav_menu`, `save_menu_item`, `delete_menu_item`, `assign_menu_location` |
| Theme / Astra | 6 | `get_theme_mods`, `set_theme_mod`, `get_astra_setting`, `set_astra_setting`, `get_custom_css`, `set_custom_css` |
| Reusable blocks | 4 | `list_reusable_blocks`, `get_reusable_block`, `save_reusable_block`, `delete_reusable_block` |
| Site identity | 2 | `get_site_identity`, `set_site_identity` |
| Widget areas | 2 | `list_sidebars`, `get_sidebars_widgets` |
| Plugin files | 5 | `plugin_list_files`, `plugin_read_file`, `plugin_write_file`, `plugin_download_url`, `plugin_delete_file` |
| Theme files | 3 | `theme_list_files`, `theme_read_file`, `theme_write_file` |
| Uploads & retention | 6 | `uploads_list_files`, `uploads_delete_file`, `uploads_delete_batch`, `uploads_retention_get`, `uploads_retention_set`, `uploads_retention_run_now` |
| WordPress updates | 5 | `wp_check_updates`, `wp_get_plugin_versions`, `wp_update_plugin`, `wp_update_theme`, `wp_update_core` |
| WooCommerce | 9 | `woo_list_products`, `woo_get_product`, `woo_update_product`, `woo_list_categories`, `woo_get_category`, `woo_list_orders`, `woo_get_order`, `woo_update_order_status`, `woo_add_order_note` |

All names carry the `pps_` prefix by default.

### Conditional groups

Two groups only register when their dependency is present, because a tool that
can only ever answer *"WooCommerce is not active"* is worse than an absent tool:

- **`woo_*` (9)** — requires WooCommerce. **Lee's Trees does not have
  WooCommerce installed**, so these will not appear. Install WooCommerce and
  they register automatically.
- **`get_astra_setting` / `set_astra_setting` (2)** — require Astra. Lee's Trees
  runs Astra Pro, so these do register.

On Lee's Trees as it stands today you should therefore see **39** new tools
(48 − 9 Woo), for a total of 82. Everything else is unconditional.

## Configuration

Both optional, in `wp-config.php`:

```php
// Rebrand the tool names. Default 'pps_' for drop-in parity with staging.
define( 'LTAZ_MCP_PREFIX', 'ltaz_' );

// Pin which theme directory the theme_* tools may write to.
// Defaults to the active stylesheet (the child theme when one is active).
define( 'LTAZ_MCP_THEME_SLUG', 'astra-child' );
```

## The other 15 tools

Staging's remaining tools — `create/get/list/update/delete` × `posts`, `pages`,
`media` — are **not custom code**. They are generated by AI Engine's own
`Meow_MWAI_Labs_MCP_Rest` class (`ai-engine/labs/mcp-rest.php`), which walks the
WordPress REST API and builds one tool per route. The resource list is hardcoded
to `posts`, `pages`, `media`.

This is not a version gap: staging runs AI Engine **3.7.0** and Lee's Trees runs
**3.7.1**, so Lee's Trees is actually the newer of the two. The tools are gated
by an AI Engine MCP setting, so enabling that option in **AI Engine → Settings →
MCP** on Lee's Trees should surface all 15 with no code at all.

Reimplementing them here would have produced 15 duplicate tools shadowing
AI Engine's own, so the plugin deliberately leaves them alone.

## Deviations from the PPS original

This is a port of Priority Print MCP Tools v1.8.0 with four deliberate changes:

1. **Theme scope.** PPS hardcodes `ALLOWED_THEME_SLUG = 'priority-print'`. Here
   it defaults to the active stylesheet, overridable via `LTAZ_MCP_THEME_SLUG`.
   Note that editing a parent theme you did not author means the next theme
   update overwrites your changes — use a child theme.

2. **Path containment hardening.** The original's theme and plugin helpers test
   containment with `strpos( $check, $root ) !== 0`, a bare prefix match that
   also accepts a sibling directory sharing the prefix (`wp-content/plugins-old`
   passes for root `wp-content/plugins`). The original's own header notes the
   uploads helper uses a stricter test; this port applies that stricter test —
   exact match or trailing separator — to all three.

3. **Empty-schema fix.** `pps_uploads_retention_get` declared
   `'properties' => array()`, which JSON-encodes as `[]` rather than `{}`. MCP
   schema validators reject that — AI Engine's own `mcp-rest.php` carries a
   `normalize_schema_node()` method specifically to avoid it. Fixed at the
   declaration, plus a normalization pass in `register_tools()` so it cannot
   recur.

4. **Namespaced options.** Retention keys are `ltaz_uploads_retention` and
   `ltaz_uploads_retention_log` (cron `ltaz_uploads_retention_run`) so they can
   never collide with a PPS install.

Items 2 and 3 are upstream bugs; they are worth folding back into the PPS
original.

## Safety model

Inherited from the original and preserved:

- Theme writes restricted to the one allowed theme directory; plugin writes,
  downloads and deletes restricted to `wp-content/plugins`; uploads tools
  restricted to `wp_upload_dir()['basedir']`. Traversal blocked via `realpath()`.
- `plugin_download_url` — HTTPS only, 12 MB cap, 60 s timeout.
- `plugin_delete_file` — single files only; refuses directories, this plugin's
  own file (matched by `realpath( __FILE__ )`, so renaming is safe), and any
  active plugin's entry file.
- `uploads_delete_*` — explicit paths only, never globs; refuses directories,
  directory-guard files (`index.php`, `index.html`, `.htaccess`, `web.config`)
  and any file still backing a media attachment. Batch caps at 500 and reports
  per-file failures instead of aborting.
- **Uploads retention ships OFF**, dry-run ON, no directory — inert until
  deliberately configured. Floors `min_age_days` at 30, caps deletes per run,
  and logs every run.
- Every write/download/delete calls `opcache_invalidate()`.
- Each tool declares `readOnlyHint` / `destructiveHint` / `openWorldHint`.
- Update tools wrap WordPress's own `Plugin_Upgrader` / `Theme_Upgrader` /
  `Core_Upgrader`.

Authentication is entirely AI Engine's MCP bearer token — this plugin adds no
endpoint of its own.

> **Blast radius.** This surface can write arbitrary PHP into plugin and theme
> directories and update WordPress core. That is the same power staging has, and
> it is the point of the parity exercise, but it is worth being deliberate about
> which site a given MCP client is pointed at.

## Tests

```
php tests/schema-check.php
```

Runs without WordPress. Asserts the advertised surface is exactly staging's 48
tools, that every schema is well-formed and JSON-safe, and that every advertised
tool is wired to a handler that exists. Handler bodies need a real site.

## Verification status

Verified statically: 48/48 tool names and argument names match staging, all
handlers wired, schemas valid, gating and prefix override behave, and the file
passes `php -l` on PHP 8.4.

Not yet verified: the plugin has **not been installed or executed on a live
WordPress site**, so handler bodies are unexercised at runtime. Install on
staging or a clone before pointing anything at production, and smoke-test the
read-only tools (`pps_list_nav_menus`, `pps_get_site_identity`,
`pps_list_sidebars`) first.
